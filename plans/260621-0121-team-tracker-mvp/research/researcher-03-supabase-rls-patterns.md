# Supabase RLS Patterns for Single-User Private App

## 1. Canonical RLS Policy Pattern (SELECT/INSERT/UPDATE/DELETE)

### Basic Pattern: Single Combined Policy
For a single-user app where every table has `user_id` column:

**SQL:**
```sql
-- Enable RLS on table
ALTER TABLE employees ENABLE ROW LEVEL SECURITY;

-- Single combined policy for all operations
CREATE POLICY "Enable full access based on user_id"
ON employees
FOR ALL
USING ((select auth.uid()) = user_id)
WITH CHECK ((select auth.uid()) = user_id);
```

### Why This Works
- `USING` filters SELECT, UPDATE, DELETE (which rows the user can see/modify)
- `WITH CHECK` validates INSERT/UPDATE (ensures new/modified rows match policy)
- Combined policy reduces redundancy for single-user apps
- `(select auth.uid())` wraps the function to enable Postgres InitPlan caching — **critical for performance**

### Performance Pattern: The auth.uid() Wrapper
**DO THIS:**
```sql
USING ((select auth.uid()) = user_id)
```

**NOT THIS:**
```sql
USING (auth.uid() = user_id)
```

The wrapped pattern allows Postgres optimizer to cache the result once per query instead of calling the function on each row. On large tables (100K+ rows), this yields **100x+ performance improvement**.

**Source:** [dev.to: 76 RLS policies rewritten — auth.uid() init-plan trap](https://dev.to/arvavit/76-rls-policies-rewritten-in-one-migration-the-authuid-init-plan-trap-in-supabase-4hg)

### Required Index
```sql
CREATE INDEX idx_employees_user_id ON employees(user_id);
```
Index on the policy column is **mandatory** for performance. Without it, Postgres must seq-scan every row.

## 2. Child Tables Without Direct user_id: Denormalize vs EXISTS

### Scenario
- `EMPLOYEE` has `user_id` (owner)
- `ENTRY` belongs to `EMPLOYEE` (via `employee_id` FK)
- `GOAL` belongs to `EMPLOYEE` (via `employee_id` FK)
- `EMPLOYEE_TAG` join table: `(employee_id, tag_id)`

### Option A: Denormalize (Recommended for Single-User App)
Add `user_id` column to all child tables.

```sql
ALTER TABLE entries ADD COLUMN user_id uuid NOT NULL;
ALTER TABLE goals ADD COLUMN user_id uuid NOT NULL;
ALTER TABLE employee_tags ADD COLUMN user_id uuid NOT NULL;

-- Simple policy for each child table
CREATE POLICY "User can access own entries"
ON entries
FOR ALL
USING ((select auth.uid()) = user_id)
WITH CHECK ((select auth.uid()) = user_id);

-- Set via trigger on insert
CREATE TRIGGER set_entry_user_id
BEFORE INSERT ON entries
FOR EACH ROW
EXECUTE FUNCTION set_user_id_from_parent();
```

**Trade-offs:**
- ✅ Simple policies (no subqueries)
- ✅ Fast queries (direct index on user_id)
- ✅ No RLS recursion issues
- ❌ Denormalized (minor redundancy)
- ❌ Must maintain consistency via trigger

### Option B: EXISTS Subquery (More Flexible, Slower)
```sql
-- No user_id on child table
CREATE POLICY "User can access own entries"
ON entries
FOR ALL
USING (
  employee_id IN (
    SELECT id FROM employees
    WHERE (select auth.uid()) = user_id
  )
)
WITH CHECK (
  employee_id IN (
    SELECT id FROM employees
    WHERE (select auth.uid()) = user_id
  )
);
```

**Trade-offs:**
- ✅ Single source of truth (user_id on parent only)
- ✅ More flexible (easier to change ownership)
- ❌ Requires subquery + index on employees(id) and entries(employee_id)
- ❌ RLS applies to subquery too (can create circular dependency edge cases)
- ❌ Slower on large datasets (subquery per row before filtering)

### Recommendation: **Denormalize**
For single-user app: denormalize `user_id` onto all tables. Simpler, faster, no RLS recursion risk. The redundancy cost is negligible for single-user scope.

**Source:** [Convene: RLS Practical Guide](https://getconvene.com/blog/supabase-row-level-security)

## 3. Setting user_id on INSERT

### Option A: Column DEFAULT (Recommended)
```sql
CREATE TABLE entries (
  id bigint PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  employee_id bigint NOT NULL REFERENCES employees(id),
  user_id uuid NOT NULL DEFAULT (auth.uid()),
  content text NOT NULL,
  created_at timestamptz DEFAULT now()
);

-- RLS policy still required
CREATE POLICY "entries_insert"
ON entries
FOR INSERT
WITH CHECK ((select auth.uid()) = user_id);
```

**Why this works:**
- `DEFAULT auth.uid()` automatically sets the column on insert
- `WITH CHECK` policy validates the user can't manually override it
- Triggers are unnecessary

### Option B: Trigger (NOT Recommended)
```sql
CREATE OR REPLACE FUNCTION set_user_id()
RETURNS TRIGGER AS $$
BEGIN
  NEW.user_id := auth.uid();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_set_user_id
BEFORE INSERT ON entries
FOR EACH ROW
EXECUTE FUNCTION set_user_id();
```

**Problem:** Triggers fire before RLS validation. If `auth.uid()` is NULL (unauthenticated), the DEFAULT is safer (stays NULL, fails WITH CHECK). Triggers hide this bug.

### Recommendation: **Column DEFAULT**
Use `DEFAULT auth.uid()` + WITH CHECK policy. Simpler, explicit, no trigger overhead.

**Source:** [Supabase Docs: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 4. Foreign Key to auth.users(id)?

### Yes, Use FK
```sql
CREATE TABLE employees (
  id bigint PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  user_id uuid NOT NULL UNIQUE REFERENCES auth.users(id) ON DELETE CASCADE,
  name text NOT NULL,
  created_at timestamptz DEFAULT now()
);
```

**Benefits:**
- ✅ Data integrity (user_id must exist in auth.users)
- ✅ ON DELETE CASCADE: clean up employee records if user is deleted
- ✅ Indexes on FK columns improve RLS query performance
- ✅ Postgres can use FK relationship info for query optimization

**Caveat:** Only use FK on the parent table that directly maps to `auth.users`. Child tables reference the parent, not auth.users directly.

**Source:** [Supabase Docs: Performance and Security Advisors](https://supabase.com/docs/guides/database/database-advisors)

## 5. Migration Workflow (Supabase CLI)

### Greenfield Project Setup

```bash
# 1. Initialize Supabase in project
supabase init

# 2. Create first migration
supabase migration new create_employees_table

# 3. Write migration file: supabase/migrations/20260621123456_create_employees_table.sql
```

**Migration File Template:**
```sql
-- supabase/migrations/20260621123456_create_tables_and_rls.sql

-- 1. Create tables
CREATE TABLE public.employees (
  id bigint PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  user_id uuid NOT NULL UNIQUE REFERENCES auth.users(id) ON DELETE CASCADE,
  name text NOT NULL,
  created_at timestamptz DEFAULT now()
);

CREATE TABLE public.entries (
  id bigint PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  employee_id bigint NOT NULL REFERENCES employees(id) ON DELETE CASCADE,
  user_id uuid NOT NULL DEFAULT (auth.uid()),
  content text NOT NULL,
  created_at timestamptz DEFAULT now()
);

-- 2. Enable RLS
ALTER TABLE public.employees ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.entries ENABLE ROW LEVEL SECURITY;

-- 3. Create indexes
CREATE INDEX idx_employees_user_id ON employees(user_id);
CREATE INDEX idx_entries_user_id ON entries(user_id);
CREATE INDEX idx_entries_employee_id ON entries(employee_id);

-- 4. Create policies
CREATE POLICY "enable_all_employees"
ON employees
FOR ALL
USING ((select auth.uid()) = user_id)
WITH CHECK ((select auth.uid()) = user_id);

CREATE POLICY "enable_all_entries"
ON entries
FOR ALL
USING ((select auth.uid()) = user_id)
WITH CHECK ((select auth.uid()) = user_id);
```

### Testing Locally
```bash
# Apply migrations to local Postgres
supabase db reset

# Verify schema
supabase db diff

# Push to production
supabase db push
```

### Seeding Sentiment Options

**Choice: Seed at Migration Time (Simplest)**

```sql
-- In migration file: supabase/migrations/20260621123457_seed_sentiment_options.sql

INSERT INTO public.sentiment_options (name, emoji)
VALUES
  ('Very Positive', '😄'),
  ('Positive', '🙂'),
  ('Neutral', '😐'),
  ('Negative', '😟'),
  ('Very Negative', '😢')
ON CONFLICT (name) DO NOTHING;
```

**Why NOT app-side seed on first login:**
- Migration-time seed is idempotent (safe to re-run)
- No race conditions (multiple users signing up simultaneously)
- Sentiment options are **app-wide constants**, not user-specific
- Single source of truth (no app logic needed)

**Note:** If sentiment options need `user_id` (unlikely for a config table), create them as a seeded lookup table without RLS, or use a SECURITY DEFINER function to insert them.

**Source:** [Supabase Docs: Database Migrations](https://supabase.com/docs/guides/deployment/database-migrations)

## 6. Common Pitfalls & Prevention

### Pitfall 1: Enable RLS Without Policies
**Problem:** Table is locked to everyone (default-deny).
```sql
ALTER TABLE employees ENABLE ROW LEVEL SECURITY;
-- No policy added → SELECT returns 0 rows, even for auth users
```

**Prevention:** Always add policies immediately after enabling RLS in same migration.

**Source:** [Supabase RLS Guide: Policies That Actually Work](https://designrevision.com/blog/supabase-row-level-security)

### Pitfall 2: service_role Key Exposed to Client
**Problem:** service_role bypasses ALL RLS. If leaked in frontend code, attacker has full DB access.
```javascript
// NEVER EVER DO THIS
const client = createClient(url, 'sbpb_service_role_key_here');
```

**Prevention:**
- Keep `service_role` server-side only (backend, Edge Functions)
- Use `anon` key in frontend (scoped by RLS)
- Rotate keys immediately if exposed

**Source:** [Supabase Docs: Exposed API Keys](https://ptkd.com/journal/supabase-anon-key-vs-service-role-key-security)

### Pitfall 3: Missing Indexes on Policy Columns
**Problem:** Seq-scan on every query. 1M row table = 1M row checks.
```sql
-- WRONG: No index
CREATE POLICY "entries_policy"
ON entries
FOR ALL
USING ((select auth.uid()) = user_id);

-- RIGHT: Index created
CREATE INDEX idx_entries_user_id ON entries(user_id);
```

**Prevention:** Always create index on policy column in same migration.

### Pitfall 4: Forgetting WITH CHECK for Child Tables
**Problem:** Can INSERT rows with wrong user_id because INSERT only checks WITH CHECK, not USING.
```sql
-- WRONG: Missing WITH CHECK
CREATE POLICY "entries_select"
ON entries
FOR SELECT
USING ((select auth.uid()) = user_id);
-- INSERT is allowed with any user_id!

-- RIGHT: Complete policy
CREATE POLICY "entries_all"
ON entries
FOR ALL
USING ((select auth.uid()) = user_id)
WITH CHECK ((select auth.uid()) = user_id);
```

**Prevention:** Always use FOR ALL with both USING and WITH CHECK for single-user app.

### Pitfall 5: auth.uid() Returns NULL for Unauthenticated Users
**Problem:** Policy `auth.uid() = user_id` silently fails (NULL = uuid is always false).
```sql
-- Problem: No explicit NULL check
USING (auth.uid() = user_id)
-- For anon user: NULL = user_id → FALSE → query returns 0 rows (silent fail)

-- Better: Explicit check (optional for RLS-first, but good practice)
USING (auth.uid() IS NOT NULL AND auth.uid() = user_id)
```

**Prevention:** If using RLS-only (no check for auth), silent fail is actually desired (unauthenticated users get 0 rows). If combining with other auth logic, add explicit NULL check.

**Source:** [Supabase Docs: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)

## Summary: Recommended Stack for This App

| Aspect | Recommendation | Rationale |
|--------|---|---|
| **Policy Pattern** | Combined FOR ALL with wrapped auth.uid() | Simple, performant, single rule per table |
| **Child Tables** | Denormalize user_id + simple policy | No RLS recursion, fast index lookups, minimal complexity |
| **INSERT user_id** | Column DEFAULT auth.uid() | Automatic, explicit, no trigger overhead |
| **FK to auth.users** | Yes, ON DELETE CASCADE | Data integrity + query optimization |
| **Migrations** | supabase/migrations/*.sql + seed.sql | Version-controlled, reproducible, testable |
| **Sentiment Seed** | Migration-time INSERT (idempotent) | No race conditions, app-wide constant |
| **Index Strategy** | One index per user_id + FK columns | RLS performance essential, FKs benefit too |
